# AWiki 消息同步显式协商 v1

- 状态：草案 / 未发布
- Profile：`awiki.message-sync.explicit-negotiation.v1`
- 范围：`anp.sync.local.v2` 的显式 logical lane 协商与有界 Ordinary 恢复
- 英文镜像：[AWiki Message Sync Explicit Negotiation v1](../../../message/vnext/10-message-sync-explicit-negotiation.md)

## 1. Discovery

客户端使用 extended bootstrap 前，**MUST** 通过只读 `anp.get_capabilities` 精确发现本 Profile。Discovery **MUST NOT** 创建或修改 replica、cursor、lane stream、activation、recovery session、backlog 或 sync timestamp。

缺少 Profile、method-not-found、无效能力响应或网络失败均表示 extended negotiation 不可用。请求空集或部分 lane 的客户端 **MUST NOT** 回退到会隐式启用 lane 的 legacy bootstrap。

## 2. Bootstrap 协商

Legacy bootstrap capabilities 保持封闭的两字段形态，携带 `p6_delivery` 时为三字段：

```json
{
  "sync_profile": "anp.sync.local.v2",
  "event_schema_max": 1,
  "p6_delivery": "p6.delivery_context.v1"
}
```

`requested_sync_capabilities` 字段存在即选择 extended shape。它固定为三字段，请求 P6 时为四字段：

```json
{
  "sync_profile": "anp.sync.local.v2",
  "event_schema_max": 1,
  "requested_sync_capabilities": []
}
```

只识别：

- `lanes.p5_device.v1`
- `lanes.p6_group.v1`
- `p6.delivery_context.v1`

`lanes.p6_group.v1` 与 `p6.delivery_context.v1` **MUST** 成对出现。未知值、重复值、P6 未配对或额外字段返回 `4200 / sync.invalid_request`；Service 不做静默子集协商。

Service 按精确 `(account_id, device_id, auth_generation, client_instance_id)` 保存完整 requested/negotiated set 和 `activation_state = active | suspended`。包括空集在内的 extended row 是唯一权威，禁止与 legacy 状态 union；合法 extended bootstrap 会把该行置为 `active`。

同一 installation 已存在 extended row 后又发送 legacy bootstrap 时，Service **MUST** 把预期为 `active` 的行原子更新为 `suspended`，保留两个 capability set，并返回 `4220 / sync.client_upgrade_required`。Suspended row 拒绝全部 fresh P5/P6 producer 写入，只有再次成功执行合法 extended bootstrap 才能恢复 active。从未存在 extended row 的 installation 保持冻结的 legacy 行为。

Extended response 的 `sync_capabilities` 是权威 negotiated logical-lane set。`lanes` 只包含匹配的 `p5_device` 和/或 `p6_group` cursor section。只有已协商 P6 才返回 `p6_delivery`。空集响应包含 `"sync_capabilities": []`，并省略 `lanes` 与 `p6_delivery`。

`sync.delta` 不重复 requested set，而是读取精确持久化协商，只接受并返回其中的 lane；只有已协商 P6 时才复用现有 `p6_delivery` context 对象。

## 3. Producer Gate

所有 fresh P5/P6 delivery、notice、retry 或 redelivery 在 durable accepted 前读取同一个权威协商仓库；只有 row 为 `active` 且 negotiated set 包含目标 lane 时才放行。completed 幂等操作先重放原结果。拒绝不得创建 delivery、lane 或 backlog row。不存在 extended row 的 replica 保持旧客户端所需的冻结 legacy 行为。

## 4. Lane 隔离与 Durable Handoff Contract

Ordinary event 独立于 requested lane section 解码和提交。unknown 或 unrequested lane 不 ACK；requested lane malformed 只使该 lane 失败。

每个 P5/P6 transport envelope 包含：

```text
lane_kind, lane_epoch, position, event_id, event_type,
raw_payload, replica_binding, created_at, expires_at
```

V1-A 冻结以下本地 handoff transaction；runtime 由后续 consumer 阶段实现：

```text
BEGIN
  把完整 raw JSON payload 写入 sync_lane_inbox
  校验 expected logical-lane cursor
  更新该 cursor
COMMIT
```

同一 lane、epoch、event ID、position 的 duplicate 使用 JSON 结构等价判断。同一 event ID 或 position 的不同 payload 是本地 `lane_input_conflict`，不得推进 cursor。Crypto、MLS、projection、rejoin 与 consumer disposition 位于该事务之外，不决定 sync cursor。

## 5. 固定 Ordinary Snapshot

Snapshot schema 2 只包含四个 authority domain：

- `read_states`
- `groups`
- `recent_plain_messages`
- `unexpired_system_notifications`

它是单一且不可 partial 的响应。recent plaintext message 使用固定 48 小时窗口，最多 500 项，第 501 项存在即整体失败；exact-device notification 最多 100 项；完整编码响应最多 16 MiB。实现使用稳定排序与 `limit + 1` 检测溢出。

- notification 溢出：`4218 / sync.snapshot_notification_limit_exceeded`
- message item 或完整响应溢出：`4219 / sync.snapshot_response_limit_exceeded`

任一错误都不返回 partial Snapshot，客户端也不采用新 cursor。应用 Snapshot 只替换这四个 domain 内由 sync 拥有的 projection，并保留 older history、draft、outbox、本地配置和 `sync_lane_inbox`。

## 6. Core 调度 Profile

一次 Core run 最多处理 20 页或 20 秒，以先到者为准。预算耗尽时持久化 `sync_pending=true` 与 continuation。同一 failure fingerprint 每 run 最多尝试三次，服务端 `retry_after` 最多等待 30 秒。持有本地 projection transaction 时禁止网络 I/O。

App 先调用 Core；patch readiness 不是前置条件。watchdog 为 30 秒。超时后 detach 旧 Future，run generation 必须阻止 late result 更新当前 UI 或清除当前 pending。
